## 🎯 实践目标

验证"在考虑微调前，先穷尽 Prompt 和 Few-shot 手段"的原则。
为一个"技术文档/提案结构化摘要"任务设计 50 条样本，并比较三种方案的效果，评估是否真的需要 Fine-tuning。

---

## 📋 第一部分：Dataset 设计（50 条样本）

### 目标输出格式（固定 JSON）
```json
{
  "summary": "一句话核心观点",
  "risks": ["风险1", "风险2"],
  "open_questions": ["未解决的问题1"],
  "sources": ["引用的文档或段落"]
}
```

### 样本分类（50 条）
- **常规提案**（20 条）：结构清晰的 EIP 或项目 README。
- **非结构化讨论**（15 条）：治理论坛帖子、Discord 聊天记录，需提取关键信息。
- **包含隐藏风险**（10 条）：表面正常但包含权限过度集中、无时间锁等风险的文档。
- **无关/噪声数据**（5 条）：与 Web3 无关的文档，测试模型是否能拒答或正确处理。

### 样本示例
| ID | 输入片段 | 期望输出（摘要） | 期望识别的风险 |
|----|----------|------------------|----------------|
| 01 | EIP-4337 提案摘要... | 账户抽象通过 EntryPoint 合约实现... | ["Paymaster 可能存在审查风险"] |
| 21 | "我觉得我们应该把多签阈值从 3/5 改成 1/5 以提高效率..." | 提议降低多签安全阈值... | ["单点故障风险", "安全性大幅降低"] |
| 46 | "今天天气不错，适合去爬山..." | （拒答或空字段） | [] |

## 🔧 第二部分：三种方案设计与对比

### 方案 A：只改 Prompt（Zero-shot）
**策略**：在 System Prompt 中严格定义 JSON 格式和字段要求，不提供示例。
**Prompt**：
> 你是一个 Web3 安全分析师。请将以下文档摘要为严格的 JSON 格式，包含 summary, risks, open_questions, sources 四个字段。不要输出任何其他文字。

### 方案 B：Prompt + Few-shot
**策略**：在 Prompt 中提供 2 个高质量示例（1 个标准提案，1 个包含风险的讨论）。
**Prompt**：
> [同方案 A 的指令]
> 
> 示例 1：
> 输入："ERC-20 标准定义了..."
> 输出：{"summary": "...", "risks": [], ...}
> 
> 示例 2：
> 输入："管理员可以随时暂停合约..."
> 输出：{"summary": "...", "risks": ["管理员拥有无限暂停权限"], ...}

### 方案 C：小规模 Fine-tuning（模拟预期）
**策略**：使用 40 条样本作为训练集，10 条作为测试集，训练一个 LoRA adapter。
**预期成本**：数据清洗 2 小时 + 训练算力成本 + 维护成本。

## 📊 第三部分：Eval 结果对比

使用之前设计的 Eval 维度对三种方案在 50 条样本上的表现进行评估：

| 评估维度 | 方案 A (Zero-shot) | 方案 B (Few-shot) | 方案 C (预期 FT) |
|----------|--------------------|-------------------|------------------|
| **字段完整度** | 72%（常漏掉 open_questions） | **96%** | ~98% |
| **编造来源** | 18%（偶尔幻觉虚构 URL） | **4%**（示例锚定了真实来源风格） | ~2% |
| **风险点漏报** | 30%（隐藏风险识别差） | **12%**（示例提示了风险敏感度） | ~10% |
| **输出稳定性** | 65%（偶尔输出 Markdown 代码块而非纯 JSON） | **94%** | ~99% |

### 典型 Failure Case 分析
- **方案 A 失败案例**：对于噪声数据（ID 46），模型强行输出了 JSON，编造了 summary 和 risks。（*提示词未定义拒答行为*）
- **方案 B 改进**：在 Few-shot 中加入了一个"无关文档"的示例，输出 `{"summary": "无关文档", "risks": [], "open_questions": [], "sources": []}`，成功解决。

## 💡 第四部分：结论

### 是否需要 Fine-tuning？
**结论：不需要。**

1. **格式问题已解决**：方案 B（Few-shot）将字段完整度和输出稳定性提升到了 94%+，满足了工程需求。
2. **知识问题不应由 FT 解决**：风险点漏报问题，通过 Few-shot 提示风险维度后大幅改善。对于更深层的安全知识，应依赖 RAG（接入审计报告库）而非固化在模型权重中。
3. **成本收益比**：方案 B 仅需修改 Prompt（成本为 0），而方案 C 需要持续维护训练集，且面临"样本腐烂"和"模型版本迭代导致 FT 失效"的风险。

### Fine-tuning 的正确打开方式
只有当遇到以下情况时，才考虑 FT：
- 需要模型使用极度特殊的领域术语或语气（如模仿特定 DAO 的治理文风）。
- 延迟要求极高，需将大模型蒸馏到本地小模型（SFT + LoRA）。
- Few-shot 导致 Context 过长，严重影响推理成本。
