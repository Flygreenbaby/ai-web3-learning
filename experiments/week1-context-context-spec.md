# Week 1 实践：Context — 钱包授权检查 Context Spec

**对应 Handbook**: https://aiweb3.school/zh/handbook/ai/context/
**实践目标**: 为"钱包授权检查 Agent"设计上下文规范，区分每类信息的数据源层级
**场景**: 用户问"这个 dApp 要我 approve，可以签吗？"
**完成日期**: 2026-05-23

---

## 分类说明

| 标记 | 含义 | 判断标准 |
|:--:|------|------|
| 🔴 必须实时查询 | 每次请求都重新从链上/RPC 拉 | 会变、且变化影响决策——区块号、余额、allowance、交易参数 |
| 🟡 可以来自缓存 | 短时间内不变，允许缓存，但要标注时效 | 基础设施级常量——chain id、合约地址、人工维护的白名单 |
| ⚪ 不能被模型当成事实 | 模型可以读，但不能信 | 来自外部/用户/第三方——dApp 页面、用户意图、simulation 预演 |

---

## Context Spec 定稿

| # | 上下文项 | 分类 | 理由 |
|------|------|:--:|------|
| 1a | chain id | 🟡 | 主网=1，Sepolia=11155111，不变 |
| 1b | 当前区块 | 🔴 | 每 12 秒出新块，缓存即过期 |
| 2a | token 合约地址 | 🟡 | 合约部署后地址不变 |
| 2b | spender 地址 | 🔴 | 交易中 dApp 传过来，当场验证 |
| 2c | approve 数量 | 🔴 | 交易 payload 实时数据 |
| 3 | allowance 和余额 | 🔴 | 链上状态随时被其他交易改变 |
| 4 | spender 可信列表 | 🟡 | 团队维护的白名单，不频繁更新 |
| 5 | simulation 结果 | ⚪ | 预演非最终，可能与实际执行不同 |
| 6 | dApp 页面说明 | ⚪ | 不可信外部来源，可能被钓鱼篡改 |
| 7 | 用户本次意图 | ⚪ | 用户输入，可能被误导 |

---

## 设计要点

1. **实时查询占 4 项**（1b/2b/2c/3）——都是链上状态或交易当场数据，任何一项过期都可能导致错误判断
2. **缓存占 3 项**（1a/2a/4）——都是部署后不变的常量或低频更新的白名单
3. **不可当事实占 3 项**（5/6/7）——simulation 只是预演，dApp 内容可能是钓鱼，用户意图可能被误导。模型可以引用它们作为参考，但不能据此下结论
4. 符合 Handbook 分层原则：**指令层**（系统规则）→ **事实层**（链上数据 🔴🟡）→ **外部层**（不可信内容 ⚪）

---

## 练习心得

这次实践的核心收获：Context 不是把 7 样东西塞进 prompt 就完事了。每一条信息进上下文时，都必须带着一个"身份标签"——你是什么来源、多久更新、可以信到什么程度。否则模型会把"链上余额"和"dApp 说的"混在一起处理，那就不是分析风险，而是被钓鱼文案带着走。
