## 密码学（Cryptography）

### 密码学 Summary

密码学不是 Web3 的「附加知识」，而是账户、签名、资产控制的数学地基——不理解它，就看不懂钱包弹窗在让你确认什么。

### 密码学 Key Points

- **私钥 = 控制权本身**：丢失 = 永久失去资产，泄漏 = 别人拿走全部。没有「找回密码」按钮。
- **公钥 → 地址**：公钥可公开，推导出地址。地址不是「用户名」，而是一个可验证的数学标识。
- **签名 ≠ 登录**：签名是对一段具体消息的授权证明——你签的是「批准转 100 USDC 给合约 X」，不是「确认登录」。
- **哈希 = 单向指纹**：任意数据 → 固定长度输出。改一个字符输出全变。用来验证数据有没有被篡改，不能反向解密。
- **Merkle Tree = 批量验证的加速器**：用少量 proof 就能证明「某条数据属于这批数据」，不需要下载全部。空投名单、轻客户端、状态证明都用它。

### 密码学 Questions

1. 如果我丢了私钥但还记得助记词，能恢复吗？助记词和私钥之间是什么关系？
2. 签名时钱包弹窗显示的「链 ID」是什么意思？如果有人伪造一个相同合约地址但不同链 ID 的交易让我签，会发生什么？
3. Merkle Tree 的 root 存在链上，proof 由用户自己保管——如果用户丢了 proof，还能证明自己属于这批数据吗？

### 密码学 Analogy

把密码学五个概念想象成**一套房产交易系统**：

- **私钥** = 房产证原件（谁拿着谁就是房主）
- **公钥** = 房产证复印件（可以给别人看，但不能凭复印件过户）
- **地址** = 门牌号（别人可以往这个地址寄东西，但不能进去）
- **签名** = 你在合同上按的手印（证明「我同意这笔交易」）
- **哈希** = 合同内容的防伪码（哪怕改一个字，防伪码全变）
- **Merkle Tree** = 一栋楼的住户登记表，你只需要看自己那一页的证明，就能确认你在登记表里，不用翻完整栋楼的档案

### 密码学 Templates

#### 1️⃣ 私钥管理规则清单

```
- 不截图
- 不上传云盘
- 不粘贴给网页
- 不发给 AI 工具或客服
- 不放进代码仓库和 .env.example
- 不用主钱包测试陌生 dApp
```

#### 2️⃣ 签名观察练习清单

```

2. 在测试环境发起一次普通转账或消息签名

4. 写下哪些信息可以公开，哪些绝不能公开
5. 比较「签名消息」和「发送交易」的区别
```

## 钱包（Wallet）

### 钱包 Summary

钱包不是「登录按钮」——它是链上控制权的管理工具。连接、签名、交易是三种完全不同风险等级的动作。

### 钱包 Key Points

- **连接 ≠ 授权资产**：dApp 读取你的地址，不等于能动你的钱。读和写是两层权限。
- **三类动作风险不同**：连接钱包（只读）→ 签名消息（证明身份）→ 发送交易（改变链上状态）。按钮文案和确认提示应不同。
- **EOA = 私钥账户**：最常见的钱包类型，私钥控制一切。简单但脆弱——丢了私钥就永久失去资产。
- **助记词 = 恢复密钥，不是验证码**：任何网页/客服/AI 索要助记词都是钓鱼。恢复账户应该在钱包应用内部完成。
- **交易有五步，点击按钮只是开始**：发起请求 → 钱包确认 → 签名 → 广播 → 打包执行。每一步都可能失败。
- **Gas 是链上执行费**：不是给 dApp 的钱，是付给网络的。余额不足、估算不准都会导致交易失败，失败也可能消耗 gas。
- **区块浏览器是「链上真相的窗口」**：查 Status/From/To/Value/Token Transfers/Gas Used，别只信 AI 总结。

### 钱包 Questions

1. EOA 私钥丢了就永久失去资产——那多签钱包和社交恢复是怎么突破这个限制的？
2. 交易失败（revert）和交易被拒绝（reject）在链上有什么区别？gas 费是否都会被扣？
3. 如果一个 AI Agent 帮我管理钱包，它至少应该有哪些硬性限制（比如单笔上限、白名单地址）才安全？

### 钱包 Analogy

**钱包 = 你的保险柜遥控器**

- **连接钱包** = 别人看到你有保险柜（知道你的柜号），但不能打开
- **签名消息** = 你在快递单上签字（证明「这包裹是我发的」）
- **发送交易** = 你输入密码、转动把手、取出东西（真的动了柜子里的东西）
- **助记词** = 保险柜的出厂重置码——谁拿到它，谁就能换掉你的密码接管整个柜子
- **Gas** = 每次开柜都要给大楼保安的小费，不管办没办成事
- **区块浏览器** = 大楼的监控录像，所有人都能看，但不能改

### 钱包 Templates

#### 1️⃣ 钱包三类动作区分清单

| 动作 | 读/写 | 花 gas？ | 风险 |
|------|:--:|:--:|------|
| 连接钱包 | 只读 | ❌ | 低——仅暴露地址 |
| 签名消息 | 离线授权 | ❌ | 中——可能被用于身份冒充 |
| 发送交易 | 写链上状态 | ✅ | 高——转走资产、授权合约 |

#### 2️⃣ 交易状态清单（前端必须处理的 6 种状态）

```
1. 等待用户在钱包里确认
2. 用户拒绝签名
3. 交易已广播，等待区块确认
4. 交易成功
5. 交易失败或 revert
6. 交易长时间 pending，需要重试或提示用户查看 explorer
```

#### 3️⃣ 区块浏览器检查清单

```
- Status：成功还是失败
- From / To：谁发起，调用了哪个地址
- Method：调用了哪个合约方法
- Value：是否直接转了原生资产
- Token Transfers：是否发生 token 转移
- Logs：合约发出了哪些 event
- Gas Used：实际消耗了多少 gas
```

## 智能合约（Smart Contract）

### 智能合约 Summary

智能合约不是「自动合同」，是部署在链上的公开程序——它把规则变成基础设施，也把 bug 变成公共风险。

### 智能合约 Key Points

- **合约 = 链上程序，不是法律合同**：代码部署后永久运行，前端可以换，合约不能随便改。
- **Solidity 五个核心概念比语法更重要**：`storage`（链上存储）、`msg.sender`（谁在调用）、`modifier`（权限门）、`event`（日志）、`revert`（失败回滚）。
- **ABI 是接口说明书，不是安全说明书**：它告诉你能调什么函数，但不告诉你调用是否安全、对方是不是恶意地址。
- **Event 是链上日志，驱动前端和索引器**：你看到的交易历史、订单列表、数据看板，大多是通过索引 event 构建的，不是实时扫链。
- **升级 = 权限问题，不是技术问题**：谁有升级权（单个 EOA？多签？DAO？）、有没有 timelock、最坏后果是什么——这些比「能不能升级」更关键。
- **一笔投票的 8 步全链路**：前端编码 → 钱包确认 → 广播 → 打包 → EVM 执行 → 回执 → 前端更新 → 索引器读 event。合约开发不只是写 Solidity。

### 智能合约 Questions

1. 为什么 `view` 函数读取状态不花 gas，但如果在另一个写函数里调用 `view` 函数就会消耗 gas？
2. 如果一个合约「不可升级」但依赖另一个「可升级」的合约，它的规则算不算真正固定？
3. AI Agent 帮我调用合约时，ABI 能告诉它函数签名，但怎么判断这个调用是否安全？需要额外哪些上下文？

### 智能合约 Analogy

**智能合约 = 自动贩卖机**

- **Solidity 代码** = 贩卖机的电路设计图（写好后烧进去）
- **EVM** = 贩卖机的供电和运行环境
- **ABI** = 贩卖机上的按钮标签（告诉你按哪个、投多少，但不告诉你里面有没有货）
- **Event** = 贩卖机打印的小票（记录每次交易，但不改机器内部状态）
- **storage** = 贩卖机里的库存计数器（存在机器里，关机也不丢）
- **Upgrade** = 换电路板——老板能换、管理员能换、还是必须所有股东投票才能换？
- **Gas** = 每次按按钮都要投币，不管出货还是卡住

### 智能合约 Templates

#### 1️⃣ 最小 Solidity 合约

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Counter {
    uint256 public count;

    event CountChanged(uint256 newCount);

    function increment() external {
        count += 1;
        emit CountChanged(count);
    }
}
```

- `count` → 链上状态
- `increment()` → 写操作（需签名 + gas）
- `event` → 外部可索引的日志

#### 2️⃣ 合约调用全链路（8 步）

```
1. 前端读取钱包地址和当前网络
2. 前端根据 ABI 编码调用数据
3. 钱包展示交易信息，用户确认签名
4. 交易被广播到 RPC 节点
5. 验证者把交易打包进区块
6. EVM 执行合约逻辑（成功则更新状态+emit event，失败则 revert）
7. 前端监听交易回执，更新页面
8. 索引器读取 event，更新历史记录/看板
```

#### 3️⃣ 判断升级风险的 4 个问题

```
1. 升级权限在谁手里？（单个 EOA / 多签 / DAO / timelock）
2. 用户能否提前看到升级提案和新实现地址？
3. 升级能不能改变资产转移、提款、暂停或权限逻辑？
4. 如果管理员密钥泄漏，最坏结果是什么？
```

#### 4️⃣ 常见错误清单

```
- 把 view 函数和写交易混在一起
- 没有处理 decimals（amount 不是人类看到的 1.5）
- 只测成功路径
- 把 owner 当成永远可信
- 忽略事件设计
```
